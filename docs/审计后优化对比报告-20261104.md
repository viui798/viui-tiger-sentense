## 3. 优化一：词先验 bloom（影响最大）

### 3.1 旧实现

`tiger_sentence_lexical.lua` 的 `contains()` 每次 bloom 探测都做：

- 逐字节 `text:byte(index)`；
- `2 ^ (bit % 8)` 浮点幂；
- `math.floor(byte / mask) % 2` 位判断；
- 同一文本在连续击键间反复重算，没有跨键缓存。

审计采样显示该模块占引擎解码采样 **43%**：

- `hashes()` 21.4%
- `contains()` 14.7%
- `score()` 5.9%

### 3.2 新实现

- `hashes()` 改为一次 `string.byte(text, 1, #text)` 批量取字节；
- 位判断改为 `POW2` 查表 + 整数取模；
- 增加跨键 memo：
  - 挂在 `model` 上，不同模型（测试夹具）不会互串；
  - 封顶 16384 条，满后停止新增；
- 保持 Lua 5.1/LuaJIT 兼容：没有使用 `//`，仍用 `math.floor`。

### 3.3 实测

审计 A/B（配对交错 ×5，整句流）：

| 运行时 | 变化 | 区间 |
|---|---:|---|
| 旧运行时（Squirrel 1.1.2） | **-405μs/键** | -495 ~ +469 |
| 新运行时（librime 1.17/Nightly） | **-77μs/键** | -85 ~ -68 |

单字流在两种运行时下都落在噪声带内。

本轮用同一剖析工具、同一整句码流重新采样 60 轮（4,321 个样本）：

| 源文件 | 优化后占比 |
|---|---:|
| `tiger_sentence.lua`（主引擎） | 68.9% |
| `tiger_sentence_fivegram.lua` | 15.3% |
| `tiger_sentence_lexical.lua` | **14.8%** |

> 注意：审计前 43% 是 300 轮采样，本轮是 60 轮，轮数不同；只看方向，不把
> 43%→14.8% 当作精确同比。方向与 A/B 的 -77/-405μs 一致。

### 3.4 正确性

用新旧两份实现逐文本对比 2,200 条（词库词 + 2~4 字子串）：

```text
checked=2200  contains_mismatch=0  score_mismatch=0  memo_entries=605
```

### 3.5 风险

- memo 按 model 隔离；新模型会得到新 memo；
- 封顶 16384 条，内存有界；
- 若未来模型在同一进程内被原地修改（当前没有这种用法），需要清 memo。

## 4. 优化二：`super_replacer` 选项轮询

### 4.1 旧实现

`process_rules(cand)` 对**每个候选**都遍历 rules/triggers 并调用
`ctx:get_option(trigger)`；当前 3 条规则共 5 个 trigger，部分候选还会被
`top_buffer` / `always_cands` / `lazy_cands` 多次处理。

### 4.2 新实现

在 `M.func` 每次菜单过滤开始时，先算一次 `rule_active[i]`：

- 遍历 trigger 求 `is_active`；
- 用当前 segment tags 求 `is_tag_match`；
- 候选循环只查表，不再调用 `get_option`。

### 4.3 收益与验证

- 审计估计收益 **≲100μs/菜单**；
- 未单独做绝对计时，属于结构性减少，不是主要收益项；
- 新旧实现在 `s2t` / `s2hk` / `s2tw` 三档下输出逐字一致。

### 4.4 风险

- 选项在菜单生命周期内不会变；切换开关会刷新菜单，因此本轮缓存安全；
- tag 判定仍按当前 segment 计算，不跨段复用。

## 5. 优化三：OpenCC 字典 `.ocd2`

### 5.1 改动

三个文本字典预编译为 `.ocd2`：

| 字典 | text | ocd2 |
|---|---:|---:|
| `emoji` | 401KB | 446KB |
| `PYPhrases` | 1.0MB | 971KB |
| `PYCharacters` | 746KB | 762KB |

`opencc/pinyin.json`、`opencc/emoji.json` 的 dict 全部改为 `type: ocd2`。
`.txt` 源表保留，新增生成工具：

```bash
python3 tools/build_opencc_ocd2.py .          # 生成/更新
python3 tools/build_opencc_ocd2.py . --check  # 检查产物是否落后
```

### 5.2 真实 librime 实测（开启 `pinyin`，10 键）

| 版本 | 首键 | 10 键总耗时 |
|---|---:|---:|
| text | 188–199ms | 247ms |
| ocd2 | **123ms** | **183ms** |

- 首键省 **65–76ms**；
- 后续按键不变（5–12ms）；
- 候选/注释/提交与 text 版**逐字一致**。

emoji：

- 输出逐字一致；
- 一次首键测量为 text 114ms / ocd2 134ms，属于噪声，**没有可确认的收益**
  （emoji 字典只有 401KB）。

### 5.3 收益边界

- 两个滤镜默认关闭；不开启时 OpenCC 字典根本不会加载，收益为 **0**；
- 收益是“新会话/新引擎首次启用”的一次性开销，不是每键加速；
- 实测环境每次新建进程/会话。若前端在进程内复用同一个 OpenCC 实例，收益会小一些；
- 没有测到常驻内存的可靠下降，不把“省内存”作为结论。

### 5.4 风险

- `txt` 改了必须重新生成 `.ocd2`，否则数据漂移；工具 `--check` 可检查；
- OpenCC CLI 对新配置会打印 config schema warning，但真实 librime 加载无错误、
  输出一致；
- ocd2 在 macOS Squirrel 1.1.2 已实测；Windows/移动端使用标准 OpenCC，理论上兼容，
  但**尚未在那些前端实机验证**。

## 7. 累计收益怎么理解

| 来源 | 量级 | 条件 |
|---|---|---|
| v0.3.21 翻译入口 7→1 | **-61%**（27 键 64.2→25.3ms/键） | **审计前基线，不是本次新增** |

- **持续打字速度**：主要是词先验的 -0.4ms/键（旧运行时）或 -0.08ms/键（新运行时）；
- **首次出候选**：拼音注释用户能感知 65–76ms；
- **不改变任何输入结果**。
