# 更新说明：统计与滤镜性能修复（v0.2.8.1）

日期：2026-10-11

## 背景

用户反馈：从中英混输与输入统计上线（v0.2.2，`09f731e`）起，Android（Trime/元书）与 Windows（Weasel）打字出现卡顿。经逐键基准测试（`tools/bench_tiger_sentence_lua.lua`、`bench_review_learning.lua`、`bench_key_correction.lua`）确认，**虎整句解码引擎本身没有性能回归**（本次上游升级后逐键耗时反而更低），卡顿源是辅助组件的同步文件 I/O 与简繁滤镜成本。

## 本次修复

> 汇总 5 项：①~④ 见下，⑤ `lua/tiger_sentence.lua` 中英混输英文表 init 预热（消除手机首次进英文段的 1~2s 冻结）见第 5 小节。

### 1. `lua/key_counter.lua`（v4 → v5，每键卡顿主因）

- **原状**：每个按键同步执行 2 次 `io.open + write + close`（`kc_count.txt` + `kc_total.txt`）；退格还会整读重写 `kc_count.txt`。Windows 上每次文件写入经 Defender 实时扫描，单键延迟数十毫秒。
- **修复**：pending 计数全部内存累计，`rest` 累计按「上屏批 + ≥60s 或 ≥120 字节」阈值落盘（`M.count()` 触发立即落盘保证外部读取精确）。
- **按键分类逻辑一字未改**（修饰键过滤 / keyup 过滤 / 次选去重 / 选字键动态收集 / Esc / 空删静默）。
- **对外 API 语义保持一致**：`take` / `restore_last` / `reset` / `count` / `status` / `last_key` 的返回值与 v4 相同（已用行为测试逐项验证）。
- 已确认当前 `input_statistics` 4.2 版不读取本模块输出（它用 translator 自算触键数），v4 的文件-IPC 设计没有现存消费方。
- 唯一行为差异：进程被强杀时，最后一个未落盘周期的击键（≤120 键）不进累计文件。

### 2. `lua/input_statistics.lua`（每次上屏全量写档 → 节流）

- **原状**：`commit_notifier` 每次上屏都把整个统计表序列化后整体重写 `input_stats_<方案>.lua`，档案随使用时间增长，手机上表现为「每上屏一顿、越用越卡」。
- **修复**：新增 `request_save()` 脏标记节流，距上次落盘 ≥30s 才写；用户指令（`//07` 清空、切皮肤等）仍即时写；`fini`（正常退出/切方案）补写脏数据，不丢记录。
- **验证**：冒烟测试 3 用例（首提交不写盘 / 阈值到即写 / fini 补写）全部通过。

### 3. `lua/wanxiang/super_replacer.lua`（简繁滤镜）

- `MAX_LOOKAHEAD` 由硬编码 16 改为可配置：方案里 `super_replacer/max_lookahead`（默认 16；**手机/低配部署建议 8**，约省一半每键成本，覆盖约 90% 的 >6 字消歧词条）。
- `env.fmm_cache` 增加上限：`super_replacer/fmm_cache_limit`（默认 20000，触顶清空重建）。该缓存会话内无上限累积，是繁体档「越打越卡」的直接来源。
- 转换结果不变（窗口默认仍是 16、缓存只影响内存占用）。

### 4. `lua/db.lua`（重码组句提示）

- 组合 DFS 增加展开节点硬上限 `MAX_DFS_NODES = 2000`（`CONFIG` 内）。`MAX_COMBINATIONS` 只限结果条数，不限制搜索量；重码很多的整句搜索最坏仍可很慢，此处早退防单键超时。
- 正常候选菜单的重码提示不变。

### 5. `lua/tiger_sentence.lua`（第 5 项：中英混输首键冻结）

- **原状**：英文词典前缀索引（`dicts/en.dict.yaml` 1.3MB）与释义表（`lua/data/english_chinese.txt` 1.3MB/7 万条）在打字**中途**惰性解析——桌面首次进英文段 ~180ms，手机 1~2 秒整帧冻结；Trime 等前端进程常被系统杀掉，每次重新唤起输入法后的第一次中英输入都要重新承受一遍。
- **修复**：方案 `init`（会话建立、用户尚未按键）时预热两张表（`M.prewarm_inline_english_tables()`）；打字路径只剩哈希查询，联想结果与释义完全不变。
- 冒烟 + 契约测试 26 用例 / 102 检查通过。

## 未改动 / 排查确认无问题

- 虎整句解码引擎、学习库、按键纠错、中英混输、造词、反查、快符、拆字、时间日期、计算器：均有门控或缓存，基准测试确认不构成卡顿源。
- 英文词典释义表 1.3MB：惰性加载，每会话第一次进英文模式有一次性小停顿，可接受。

## 验证

- `tools/test_rime_contract.lua`：26 用例 / 102 项检查通过。
- `key_counter` 行为语义测试 13 项断言通过；`input_statistics` 节流 3 用例通过；`fmm_cache` 触顶逻辑 1 用例通过。

## 升级方式

与平时相同：更新修改过的 Lua 文件到 Rime 用户目录，重新部署。建议手机端同时在方案补丁（`tiger_sentence.custom.yaml`）加：

```yaml
patch:
  tiger_sentence/perf_log: true        # 诊断用：每次上屏写一行性能数据，定位完删掉
  tiger_sentence/memory_profile: balanced   # 手机：模型页缓存 2MB→8MB，减少翻页
  super_replacer/max_lookahead: 8      # 手机：简繁窗口档位
```

写出来的文件：用户目录下 `tiger_perf_log.txt`，每行一次上屏：

```text
t=<时间戳> calls=<本次上屏的解码次数> total=<解码总耗时ms> max=<单次最大ms> page=<模型翻页读取KiB> heap=<Lua堆MiB> ev=... iso=...
```

## 性能预期

| 路径 | 修复前 | 修复后 |
|---|---|---|
| 每按键（Windows/Android） | 2 次文件 open+write+close | 0 次 |
| 每次上屏 | 统计档全量重写（随时间增长） | ≥30s 一次，且不变大不改慢 |
| 繁体档每键（40 候选×34 字） | ~5.5ms（窗口 16 累积缓存） | 可选窗口 8 → **~3.3ms**；缓存受控不再随会话增长 |
| 重码提示 DFS 最坏 | 不可控 | ≤2000 节点硬上限 |
