# v0.2.9 与当前虎整句的性能对比

日期：2026-11-03。旧版来自用户提供的 `/Users/viui/Downloads/cheese-tiger-v0.2.9.zip`，新版指本地 v0.3.20（HEAD `bb69c56`）加尚未发布的快符日志清理、反查模型开关。不是把未发布改动当作 GitHub 正式包。

## 结论

本机真实 librime 完整链路的三个普通虎码输入用例，新版均明显慢于旧版；纯 Lua 解码差异远小于完整链路。证据优先指向组件调度和整合处理链路的额外成本，不支持“新版换了更大的五阶模型”这一解释。尚不能据此确定安卓元书的唯一瓶颈，或承诺其慢相同百分比。

此前的 v0.3.2 对照也出现相似现象，见 [性能诊断](性能诊断-v0.3.2-v0.3.20.md)。那个对照的组件拆分实验是辅助证据，不是本次 v0.2.9 的逐模块归因。

## 文件与功能差别

旧 ZIP 的主引擎、方案、default.custom.yaml、rime.lua 均与仓库 v0.2.9 tag 相同，可用版本差异解释实际 ZIP。旧方案版本为 `1.6.20261010.3`，基于上游 `1.6.20261010.1`；当前为上游 `1.6.20261030.1`。

逐字节相同的文件包括：

- 五阶模型 `models/sentence-fivegram-mobile.bin`，405,663,171 字节，SHA-256 `756f6c92cf43ad6e8e3087ce66b711ac6ad0fc41e6f3fb82b3766e35ecab8681`。
- 虎码码表、字频排名、补充码表。
- 五阶模型读取模块、词先验模型及词先验读取模块。
- `lua/key_counter.lua`，旧版已经是内存缓冲实现，不能把该优化误算为新版新增。

| 更新 | 相对 v0.2.9 的变化 | 性能影响范围及判断 |
|---|---|---|
| 常用/全字集 | 新增字集清单、过滤及版本状态 | 建库时逐候选检查；字集改变后需要刷新索引和缓存。处理器在空输入时会打开、读取清单；相同内容不会重复解析，也不是每个字母都读文件 |
| 三档回删 | 新增回删观察和状态维护，默认整字回删 | 普通按键也有少量状态检查；没有证明是主要延迟来源 |
| ASCII 包装器 | 原生 ascii_composer 改为上游 Lua 包装原生组件 | 每键额外 Lua 调用；buffered 状态变化时重建适用的原生组件。用于避免切英文时提交内部标记，不能直接删除 |
| 学习与选项 | 首选学习的受控分支、回删/字集/辅助开关持久化 | 更多状态检查；默认 first_choice_selection=false，不能称为默认每键强化首选。Windows UTF-8 学习文件修复只针对相应文件操作，不是安卓普通每键的 locale 切换 |
| 模型拼音反查 | 原生 script_translator 路径改为独立 Lua 第二引擎、分页拼音索引 | 反查自身的计算与内存行为不同。普通虎码未匹配反查 tag 就返回，不会因此也运行一遍拼音模型；但独立翻译器入口有调用成本 |
| 虎码+拼音混输 | 新增 tiger_mixed 翻译器及临时词块解码 | 普通虎码无反引号会短路；仍有独立入口的调度成本。这里不是旧版已经移除的中英混输 |
| 全字集反查与调频 | 新增 yin_full 处理器/翻译器、reverse_freq 处理器 | 普通输入也经过部分判断；选词记录只在目标反查路径处理 |
| 统计与整段重复 | 新统计处理器、快符提交历史扫描与 ;z | update 通知中统计、重复模块各自转换及比较提交历史，普通输入也可能触发。已发现额外工作，尚未证明能解释主要差距 |
| 快符收敛 | 删除原生快符词典入口，改为 Lua 规则 | 既有减少组件，也有新增历史维护，不能按文件大小推算净性能 |
| 调试输出 | 旧 perf_diag 默认关闭，后续已移除；新版快符曾残留同步调试日志 | 当前本地已清除快符日志。此次测速仍显示回退，说明日志不是全部原因 |

白名单从 727 字节增至 755 字节（7 字），不是模型扩容。原有简繁/拆字/Emoji 等过滤器的接线顺序没有新增一整套链路；不能仅因它们存在就认定是最近回退来源。

## 完整 Rime 输入链路

使用本机 Squirrel 的 librime 和 librime-lua，在 `/tmp` 隔离目录编译方案；未使用个人学习库或改动生产鼠须管目录。当前隔离目录的主引擎、快符、方案、拼音模块与工作区逐字节一致。

计时涵盖逐键 process_key、读取/释放候选 context、读取/释放 commit；不含界面绘制和系统键盘事件传递。保持默认提前上屏开启，反查模型开启。每次 10 轮，丢弃前 3 轮；每个用例按旧→新→新→旧顺序执行，以下展示两个进程的结果范围。仅输入普通虎码，未先调用拼音反查。

| 用例 | v0.2.9 平均每键 | 当前平均每键 | v0.2.9 P95 | 当前 P95 |
|---|---:|---:|---:|---:|
| 这个问题其实没有那么复杂，27 键 | 18.805–18.882ms | 26.799–28.529ms | 36.592–39.118ms | 44.691–47.185ms |
| 今天早上我吃了两个面包，24 键 | 15.633–16.687ms | 27.961–29.691ms | 26.172–27.396ms | 44.843–58.997ms |
| 我们现在还没有，14 键 | 14.535–15.221ms | 24.944–29.652ms | 23.195–24.442ms | 39.207–55.915ms |

编码分别为 `vujgadkotwzhwwkrnvautkeohke`、`jaefmonyftuderlmljgbmnvs`、`tujanengcukrnv`。候选抓取记录最后一个残留候选，因提前上屏会拆出已提交前文，不能把记录的“复杂/包/没有”误读为只输出了这些字，也不能用此探针断言整个候选列表完全一致。

按两次平均值计算，三个用例当前平均每键耗时分别约增加 47%、78%、83%。这是这台机器、这些输入与选项下的结果；没有统计置信区间，不能概括为所有句子、所有设备统一慢某个比例。两个新版本进程间也存在明显波动。

## 纯解码复核

同一份 `tools/bench_tiger_sentence_lua.lua` 分别加载旧包和当前目录，Lua 5.5，真实模型，`--repeat 5 --burst-cases 10 --require-model`。下面采用完整链路实验结束后、无另一基准并发的复核结果。

frontend 指脚本模拟的解码/证据调用序列，数值是整段累计平均耗时，不是完整 librime 每键耗时，不可和上一表直接相减。

| 用例/指标 | v0.2.9 | 当前 |
|---|---:|---:|
| 今天早上…，frontend 整段 | 5.04ms | 5.24ms |
| 这个问题…，frontend 整段 | 6.06ms | 6.07ms |
| 他把那本书放在桌子上面然后离开了，frontend 整段 | 10.99ms | 12.40ms |
| 40 码低置信串，frontend 整段 | 16.91ms | 18.01ms |
| 10 条未预热随机 40 码串，单键 P95 | 1.05ms | 1.25ms |

当前并非每一项都完全等速，长句与未预热串存在额外耗时；但不表现为完整链路中那样的普遍大幅增长。纯解码测试没有覆盖所有上游按键、通知器和真实用户学习库，不能据此宣布主引擎没有任何退化。

## 建议

1. 首先试验减少普通虎码经过的独立 Lua 翻译器入口，以统一分派保留反查、混输全部功能。此前 v0.3.2 组件拆分中，移除拼音入口反复改善普通输入，而保留入口、仅把函数体改为空未复现同等改善；需要查调用/候选调度，不能只优化函数中的几个 tag 判断。
2. 再按隔离对照测量 ASCII 包装、字集首键读取、统计与重复历史扫描；保留上游行为，避免用删除功能换跑分。
3. 单独修复此前发现的 allow_short_key 缓存字段比较笔误，并验证普通→混输→普通的缓存语义；目前不是普通虎码卡顿的已证实主因。
4. 反查无模型开关只控制拼音第二实例，不能直接消除普通虎码的上述入口成本；也不等于退回 v0.2.9 的原生反查架构。
5. 功能回归通过后，用同一探针对照，最后在反馈者安卓元书测普通输入、首次输入和使用反查后的延迟。暂不建议缩模型、删学习库或整体回退而丢掉新版功能。
