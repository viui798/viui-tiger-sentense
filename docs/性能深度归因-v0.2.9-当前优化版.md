# v0.2.9 与当前优化版：性能深度归因

日期：2026-11-03。范围：只定位原因，不修复、不部署、不发布。

## 结论

本机最主要的耗时是 **librime-lua 在 LuaTranslation 销毁时执行全量 Lua 垃圾回收**。当前方案增加的 Lua 翻译入口，即使对普通虎码输入不产出候选，也会进入对象生命周期，从而增加这种昂贵的回收机会。不能将慢键简单归因于五阶模型推理，或统计、快符函数本身。

这是鼠须管所带插件上的已验证结论。反馈来自安卓元书，但尚无其版本、二进制或设备采样；使用相同方案不代表使用相同插件，安卓原因仍需验证。

## 测试范围与方法

旧版来自用户提供的 `cheese-tiger-v0.2.9.zip`；新版是本地 v0.3.20 加此前尚未提交的优化（含共用翻译入口、反查模型开关、快符日志清理），不是未修改的 v0.3.20 标签。

两版分别置于 `/tmp/cheese-deep-20261103/old`、`new`，使用同一本机 Rime/插件，在独立目录中清理实验学习数据并统一选项。启用提前上屏、关闭提前上屏至编码、使用简体；反查模型开关开启。模型、虎码码表、排序/补充数据及模型读取模块已核对相同。每例 10 轮，剔除前 3 轮，测量原生按键处理及上下文/提交读取。

主用例编码 `vujgadkotwzhwwkrnvautkeohke`，27 键，测量 189 键。以下为每键平均耗时（毫秒），不是安卓手机结果。

| 条件 | v0.2.9 两次运行 | 当前优化版两次运行 |
|---|---:|---:|
| 安装中的正常插件 | 18.620 / 19.946 | 28.941 / 28.398 |
| 临时副本绕过显式全量 GC | 0.693 / 0.674 | 0.745 / 0.728 |

正常插件下，新版在该例慢约 42%–55%；绕过后绝大多数差距消失。上下文读取约 0.010ms，提交读取约 0.001ms，主要耗时位于按键处理。

另外两个编码交叉验证：

| 编码 | 旧版正常 | 新版正常 | 旧版绕过 | 新版绕过 |
|---|---:|---:|---:|---:|
| `jaefmonyftuderlmljgbmnvs` | 15.822 | 24.925 | 0.631 | 0.722 |
| `tujanengcukrnv` | 16.097 | 22.315 | 0.254 | 0.354 |

绕过实验只修改 `/tmp` 中的插件副本：将 ARM64 `Lua::gc` 函数入口改为返回，Lua 自动垃圾回收仍存在。它是归因消融实验，**不是可交付的修复**：峰值 RSS 从约 32–36MB 增至约 42–48MB，尚未做长期内存和完整功能等价验证。

## 热点与二进制证据

5 秒原生采样显示链路：

```text
RimeProcessKey → LuaProcessor → Context::PushInput
→ Compose → TranslateSegments → LuaTranslator::Query
→ LuaTranslation::~LuaTranslation → Lua::gc
→ lua_gc → luaC_fullgc → singlestep / propagatemark
```

主线程 4127 个采样中，singlestep 2000、propagatemark 1407、reallymarkobject 187、luaC_fullgc 30，合计约 88%。采样含少量启动/维护工作，此比例仅说明热点，不作严格稳态时间占比。

安装插件反汇编确认析构路径无条件调用 `Lua::gc`；后者以参数 2（LUA_GCCOLLECT）调用 lua_gc。

插件：`/Library/Input Methods/Squirrel.app/Contents/Frameworks/rime-plugins/librime-lua.dylib`

SHA-256：`a0862901b4d36d35aba7012f05c132dd087890cca564609c5d1ea3ba9de7c12b`。

对照 [librime-lua 源码 6da5d6c](https://github.com/hchunhui/librime-lua/blob/6da5d6cedb853380ed1b5b9b6979cb1a9c028353/src/lua_gears.cc)，该上游版本已改成每 256 次析构全量回收，其余 gc_step(32)。因此不能用最新上游源码代替本机插件行为，也不能未经确认套用到元书。

## 方案层面怎样放大耗时

一次稳态 27 键输入引起 33 次翻译处理（包含额外重组）：旧版有 6 个 Lua translator、7 个 Lua filter；新版有 7 个 translator、相同的 7 个 filter。

插桩记录旧版 429、新版 462 次 Lua 翻译/过滤协程启动；新版额外的 `tiger_sentence_dispatch` 在普通虎码输入中调用 33 次而不输出候选。**这些是入口启动次数，不是直接测得的 GC 调用次数**。结合析构行为，可解释为什么空入口也有成本，以及之前只合并入口的优化为何有限。

此前两个反查/混输入口已合并为一个，但并未消除本机插件的频繁全量回收机制。现有过滤链也是旧版已有的共同成本。

显式 GC 后，存活 Lua 堆旧版约 11604.6KiB、新版约 12197.9KiB，相差约 593KiB；去掉空闲反查/混输模块加载只减少约 81KiB。单次 GC 测量有明显波动，不能用约 5% 的堆增长解释全部延迟差距，也不能断言反查未使用时已全量加载拼音词库。

临时移除入口、空载辅助模块、跳过历史捕获的实验存在明显机器状态波动，只用于判断方向，不将各项差值相加当成精确贡献。

## 直接回调成本

临时插桩一次 10 轮、270 键运行，累计 CPU 时间：

- 快符 capture_commits：343 次，6.804ms，约 0.020ms/次。
- 统计 capture_history：343 次，4.185ms，约 0.012ms/次。
- ASCII 回调：270 次，1.034ms，约 0.004ms/次。
- 字集 reload：12 次，4.185ms，含首次初始化。

同次正常插件测试稳态平均 22.349ms/键。两者统计窗口不同，不能直接算百分比；但回调直接耗时远小于整键耗时，不能解释数十毫秒的热点。此测量不排除其产生对象后的间接 GC 成本。

## 尚不能下的结论

1. 未取得安卓元书的插件版本或采样，不能宣称安卓卡顿已经完全定案。
2. 当前证据没有证明模型文件变大或推理算法变慢导致本轮回退；比较的模型相同。
3. 不能承诺关闭反查模型开关就能解决普通虎码卡顿：开关不等于移除 Lua 入口，也不改变插件 GC 策略。
4. 没有精确分摊新版额外延迟到每个模块；使用反查后第二实例是否进一步扩大普通输入回收成本仍待独立验证。
5. 临时绕过 GC 的候选尾项符合预期，但不等于完整输出或长期功能等价验证。
