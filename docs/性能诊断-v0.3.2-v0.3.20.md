# v0.3.2 → v0.3.20 普通整句延迟对照

日期：2026-11-03。当前源码：`bb69c56`（v0.3.20）。反馈环境：安卓元书，普通虎码整句也卡，不要求先使用反查或混输。

## 结论与证据边界

本机完整 librime 链路复现了新版普通虎码输入延迟增加；纯解码测试没有出现相同幅度的退化。应优先优化新增组件参与普通输入时的调度开销，而不是更换模型、删除学习库或直接砍掉辅助功能。

这是 macOS 无界面 librime + librime-lua 的对照，不是安卓元书实测，不包含键盘、候选窗绘制、系统调度及触屏延迟。尚未获得反馈设备上的性能采样，不能宣布已找到元书全部卡顿的唯一根因。

所有删组件、空函数、日志开关及插桩实验只在 `/tmp/cheese-latency-current` 进行；没有修改鼠须管用户目录或正式运行代码，没有部署、提交、推送或发版。

## 基准与方法

- 旧版来自用户提供的 `cheese-tiger-v0.3.2.zip`，解压到 `/tmp/cheese-latency-v032/芝士虎整-v0.3.2`。
- 当前版在隔离目录重新编译，模型使用当前工作区真实文件。
- 对照确认 `models/sentence-fivegram-mobile.bin`、`tiger_sentence.codes.txt`、`lua/tiger_sentence_fivegram.lua` 两版逐字节相同。模型仍为 405,663,171 字节五阶 Q8，并非新增更大模型。
- 隔离目录未导入个人学习库、反查调频记录和统计历史，故结果不能代表重度用户的数据规模。
- 普通输入编码：`vujgadkotwzhwwkrnvautkeohke`（这个问题其实没有那么复杂），提前上屏开启。
- 完整链路每轮清空组合，连续输入 27 键；每键计时包含 `process_key` 和读取/释放 `RimeContext`。运行 8 轮，丢弃前 3 轮，统计后 135 个键的墙钟耗时。P95 是单键分布，不是整段平均值的 P95。
- 下面正式对照逐个进程顺序执行，旧版分别在前后复测。没有通过主动选择学习来预热，但输入序列、模型页及组件缓存会预热。

## 已定位的问题与未证实猜测

### 1. 新增翻译器对普通虎码输入也有调度成本：优先调查

`tiger_sentence.schema.yaml` 比旧版新增独立的拼音反查、虎拼混输、全字集翻译器入口。

普通虎码不会进入拼音五阶解码：`lua/tiger_sentence_pinyin.lua` 先判断段 tag，未匹配即返回；`lua/tiger_mixed.lua` 无反引号也直接返回。但函数内短路仍发生在 Rime 已调用 Lua 组件之后，不等于整个入口零成本。

移除拼音接线的改善在多组中重复出现，而保留接线、只将函数体置空没有产生同等改善。证据指向组件调用/翻译调度层的额外开销，不能简单归结为“五次 has_tag 很慢”。具体 librime-lua 内部机制及元书是否更严重，还需要进一步采样。

### 2. 快符调试日志留在热路径：确定的问题，非本机主要耗时

`lua/tiger_kf.lua` 的 `capture_commits` 内残留无条件 `io.open("/tmp/kf_cap.log", "a")`、写日志、关闭文件；它在检查 `added <= 0` 之前执行。

该函数连接到 update 和 commit 通知器：普通输入也会执行，`repeat_z` 关闭不会停止历史维护或日志。Windows/安卓若没有此路径，仍会尝试打开失败；失败受保护不报错，不代表没有开销。

插桩的一段 27 键输入中，统计扫描及快符扫描各执行 36 次（含初始化和多次通知）；所有 `io.open` 合计 91 次，不能全算作调试日志。累计时间显示调试日志不足以解释本机数百毫秒的整段差距。删除日志的顺序对照也没有显示恢复到旧版速度。

### 3. 统计与重复上屏的历史扫描：有新增工作，尚未证明是主因

新版 `input_statistics` 和 `tiger_kf` 都在输入更新时调用 `commit_history:to_table()`，建立签名并比较前后历史；同一更新可能扫描两遍。

但本机插桩及临时禁用历史处理的探索性对照，没有证明它能解释主要差距。适合后续合并/减少重复扫描，不能以“看见循环”就宣布根因。保留统计精确口径和整段重复语义是优化前提。

### 4. 词库反复重建：已在当前用例排除

指令采样中，码表解析和 `learning.hash` 看似很热。进一步在 `rebuild_lexicon` 入口计数及打印调用栈，27 键过程实际只建库 1 次：首次按键初始化。

早期采样被首次建库影响，不能据此声称每键重建。旧版同样存在首用初始化开销；元书首次输入是否明显更慢，需要另测。

### 5. 另发现一处缓存条件笔误，不宜当作普通虎码卡顿结论

`lua/tiger_sentence.lua` 的两处增量缓存复用条件使用了裸变量 `allow_short_key`，而缓存写入及快速命中使用 `lexicon_state.allow_short_key`。裸变量不是该处局部变量，依赖全局值，混输带位置约束时可能错失缓存复用。

普通虎码时两者通常为 nil，当前报告不能将此笔误当作普通虎码变慢主因；但后续应修正为一致的状态字段，并增加“普通→混输→普通”及位置约束的缓存验证。

## 建议的修复顺序

1. 删除快符调试日志；保留重复上屏和快符行为，不动用户数据。
2. 减少普通输入经过的独立 Lua 翻译器入口。优先试验统一分派：同一个入口按段 tag/input 路由虎码、拼音、混输，仅在目标路径调用相应引擎。不能仅把已有函数体改成提前返回，也不能直接删除反查/混输功能。
3. 修正 `allow_short_key` 状态比较，验证所有增量缓存与混输语义；不能为了跑分改候选质量参数。
4. 视测量结果复用提交历史扫描，避免统计和重复功能重复转换同一历史；不开重复时是否维护历史，需要明确开启后的首次重复语义。
5. 优化版先跑契约和完整回归，再用本报告同一完整链路做前后对照，最后请反馈者在元书复测同一段编码、同一选项。重点记录普通输入、首次输入、用过反查后、简繁/注释开关以及真实用户学习库规模。

没有证据支持删学习库、缩减五阶模型、删除简繁/拆字/Emoji，或宣称“一定是元书软件问题”。本次仅诊断，尚未实施上述正式修复。

### 新开关完整链路对照

在同一隔离目录，真实 librime + librime-lua，顺序运行 on/off/on/off，每次 8 轮丢弃前 3 轮，计时含 process_key、候选 context 读取和 commit 读取。使用全拼。没有模拟元书 UI。

| 用例 | 模型开，平均每键（两次） | 模型关，平均每键（两次） | P95：开 / 关 |
|---|---|---|---|
| `` `nihao `` | 3.891 / 3.724ms | 2.497 / 2.672ms | 4.461–4.488 / 3.023–3.748ms |
| `` `jintianzaoshangwochilelianggemianbao `` | 4.998 / 5.186ms | 4.731 / 3.662ms | 6.210–6.488 / 5.385–9.639ms |

短反查平均约降低 32%；长句平均有下降，但无模型的一次运行仍出现 89.555ms 尖峰，P95 更高，不能保证尾延迟总是更低。两种模式在这两个样例的最终首选均为「你好」及「今天早上我吃了两个面包」，不代表其他输入候选完全一致。

普通虎码控制组也运行 on/off/on/off。开关不进入该执行路径，测得差异不能归因于是否关闭反查模型；不能以该组运行波动宣传普通虎码已提速。对照暂不分离使用反查后长时间运行的 GC、内存或系统调度影响。

原始数据：`/tmp/cheese-switch-bench.jsonl`。新增可复用工具 `tools/bench_rime_reverse.cpp`，后续加入会话重建后的选项检查，三方案 on/off 均通过。该检查版本的短反查冒烟数据不与上表混算。
